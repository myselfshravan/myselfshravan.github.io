1 · What it is

A memory and a lab for your conversations

Your chat history may be the most detailed record of your relationships that exists, and nothing reads it. Oracle reads all of it, keeps what matters, checks what it claims, and gives it back as something you can ask, search and act on.

Point Oracle at chat exports and it builds three things.

  • A living dossier for every relationship. What is happening in their life now, the story of the friendship in chapters, open threads and promises, shared jokes, what lands and what backfires. Every quote in it is checked against the source.
  • A measured model of how you communicate. Every day is scored and every reply is labelled, so you can see how you differ by person, how you change over time, and what your messages tend to cause.
  • A writing tool in your voice. Drafts are grounded in that context, tuned against your real replies, and scored before you send them.

It is a Node.js command-line pipeline with a local React viewer. There is no hosted service and no account. You bring your exports and your API keys, and everything it generates is plain files in one folder on your machine.

The project has been built and tested on one real archive: seven relationships, 129,132 messages, WhatsApp and Instagram, 2022 to 2026, in mixed languages. Every result on this page comes from that run. That is enough to show what the system can do. It is not enough to say anything about people in general.

2 · What it can do

What you can do with it

Eight capabilities, all working today. The viewer only spends money when you press a button: asking, drafting or checking a message. Everything else is already computed.

capabilitywhat you get

There are also longitudinal tools for one person across all their chats. A lifeline shows your life across every conversation and who was told what. A study called Becoming separates how you change from how you differ by relationship, and it writes a research-paper draft whose prose numbers are checked against computed facts.

3 · How it is built

How it works

A resumable pipeline of small steps. Each one writes JSON. Models do the reading, and code does everything that has to be right: dates, arithmetic, splits, weights, statistics.

Three models, each where it is strongest

modeljobwhy
Claude Opus 5.5Monthly memory, dossiers, lifeline, reply drafts, the Ask agent, the voice judgeDeep reading and writing, and the only judge that is hard to fool
Claude Haiku 5.5A one-line gist per day, topic namesLight bulk work
TypeSafe JevScores every day, labels every reply, checks quote support, re-ranks searchFast, calibrated typed judgments at $0.042 per million input tokens

Local embeddings (transformers.js with a multilingual MiniLM model) power search and topics, so that step never leaves the machine.

Model choice is measured, not assumed. Each layer tests the cheap options against Opus on the same items, then runs on the cheapest one that holds up.

Design rules that made it work

  • Typed fan-out. Each day is one request asking many small typed questions, with composite scores weighted in code. That is what makes reading every day affordable.
  • Verify in code. Every dossier quote is matched verbatim against the source, then a second model checks that the context really supports the claim.
  • Split by date hash. Train, validation and test never share a day, so nothing leaks between them.
  • Accept only on held-out gain. A voice card is kept only if its paired gain on validation exceeds one standard error. Lab effects ship only if they replicate on test days.
  • Resume everything. Every step skips finished work, so a failed run continues where it stopped. Adding a new export only processes the new messages.
  • Work inside the grammar limit. Structured outputs have a compiled size limit, so large outputs are split into parts over one cached prompt. A probe script checks each schema.

Under the hood

partdetail
PipelineAbout 4,600 lines of ESM JavaScript, Node 22+, five runtime dependencies

4 · Does it work

How we know it works

A system that reads your life can sound convincing while being wrong. So every layer has a test it can fail, and several of them did.

Can it write like you?

This is the hardest test in the project. A blind judge sees a real conversation, the reply actually sent, and a draft, and has to pick the real one. At 50% the judge is guessing. The tested judges differ a lot: Jev and Haiku rate drafts as real well over half the time, so they would be easy to game. Opus is the reward.

A first style guide did nothing. What worked was the hill climb: find the replies where the judge caught the draft, rewrite the card from those failures, and keep the change only if it wins on held-out turns. On one run, the fix it discovered on its own was "react small and literal", because drafts kept coming out over-built.

Can it separate the person from the relationship?

With one constant person across seven relationships, Oracle can split each trait into who they are with, change over time, one relationship's own arc, and noise. Time effects must beat 300 calendar shuffles and a correction for testing many traits.

On this archive, which relationship explains 44% of how the person writes, and time explains 24.5%. Six traits show change over time across all relationships. Simple word counts could not see any of this: they are 56% noise.

The same result explains a useful failure. Voice cards written for a specific year lost to no card at all.

Style lives in the relationship more than in the calendar, so a card about a year pins down the wrong thing. That is why Oracle's voice cards are built per person, not per era.

Can it measure what a message does?

Old conversations are a natural experiment, if you compare carefully. Each of 34,233 replies is compared only with other replies to the same person, in the same quarter, in the same situation. All features are fitted together, confidence intervals bootstrap whole days, and an effect ships only if it replicates on held-out days.

Sharing something of your own was the strongest lever on openness (+9 points). A reply that could read as dismissive cost 21% of a typical reply's warmth. Plenty of plausible effects, including giving advice and bringing up shared memories in ordinary conversation, did not replicate and were dropped. These are patterns from one archive, not causal laws.

Are the quotes real?

Dossiers cite real lines, and code checks them. Of 381 quotes in the seven dossiers, 380 matched word for word and one failed. In the perspective study, all 178 Opus stances had verbatim quotes, against 97% for Haiku. Requiring proof in code changes how much you can trust a summary of your own life.

Where it breaks

limitwhat happened
Voice ceilingThe best chat reached 48%, the mean 45.7%. No chat reached 50%
Cheap judgesJev and Haiku are too easy to fool to use as the reward, so voice tuning still needs Opus
Era voicesYear-specific cards performed worse than no card at all
Word countsAbout 56% noise at the day level, so they can't carry this kind of analysis
Small chatsThe smallest chat had 25 days. Per-person lab effects need far more than that
Structured outputSchemas past about 13 top-level array fields risk hitting the API's grammar limit
Mixed languageThe judges read English best, and humour in mixed-language chat is the hardest thing to score
ValidityModel agreement (r = 0.84) is not the same as being right about how anyone felt. Scores have not been validated against human coding
CausationNobody was randomised. The lab finds like-for-like patterns only
SampleEvery result here comes from one person's archive

That last row matters most. A second and third archive would tell us more than any new feature.

6 · Privacy

Making something this personal public

Oracle's input is the most private data most people own, and half of it was written by someone else. Any public version has to start from that.

Where your data goes

stepwhere it runs
Parsing, statistics, permutation tests, rankingYour machine
Embeddings and semantic searchYour machine
Viewer and generated outputsYour machine
Memory, dossiers, drafts, AskSent to Anthropic's API
Day scores, reply labels, quote checksSent to TypeSafe's API

So Oracle is not fully local today. A public release must say this plainly, and a fully local mode is on the roadmap below.

The other people in your chats

Your friends never agreed to be analysed. That problem does not go away because you own the export. The project's rules so far:

  • Descriptive, never diagnostic. Psychological outputs cite dated verbatim quotes and make no clinical claims.
  • No manipulation. The agent and the reply studio refuse to plan manipulation or coercion of a specific person.
  • Sensitive dates stay quiet. Anniversaries marked sensitive are flagged as "don't bring up casually".
  • Your own data only. The tool works from exports you already hold.

How this page was made safe

This page was produced from the real archive, so it doubles as a test of publishing results safely. It contains no names and no messages. A check script scans the page against the people, places, handles and employers in the source data, more than 400 terms, and against all 25,857 messages of 25 characters or more. The check fails if anything matches. A public version of Oracle should ship that same gate, so anyone can share their results without exposing the people in them.

7 · Open source

The path to open source

Oracle is not public yet. The code is close, and the blockers are specific. If enough people want this, here is exactly what happens next.

Already in place

  • API keys live in .env, with a .env.example template.
  • Tests use a synthetic chat and a fake model, so contributors need no keys and no private data.
  • Generated outputs are already excluded by .gitignore.
  • The name of the person being studied is a setting (ORACLE_SELF).

What has to happen first

blockerwork needed
Chat datachats/ is not in .gitignore yet. It has to be, before the first commit
LicenceNone exists yet. One has to be chosen
Personal defaultsA real name is still the default in config and in parts of the viewer and CLI. Examples in the README use real first names
Test fixturesFixtures are synthetic but still use a real first name for the main participant
Model keysThe day index and the lab need a TypeSafe key as well as an Anthropic key, and .env.example still calls TypeSafe optional
Private toolingOne-off analysis scripts stay out of the public repo
Vendored docsThe mirrored TypeSafe docs need permission, or replacing with a link
Demo dataA synthetic archive, so anyone can try the viewer before spending money
Clean repoThe project isn't under version control yet, so it can start with a clean history

What comes after

1. More importers. Telegram, iMessage, Signal and Discord are the obvious next formats. 2. A fully local mode. Run the day scoring on a local model and measure how much accuracy that costs, the same way every other model choice is measured. 3. A cost estimator. Show the expected spend for an archive before any call is made. 4. Replication on other archives. The findings on this page come from one person. A way to pool anonymous, aggregate effects across volunteers would turn a personal tool into real research. 5. Human validation. Compare model scores with people's own ratings of their conversations.

What using it would look like

cd oracle && npm install && (cd viewer && npm install && npm run build)
# put exports in chats/<name>/, keys in .env
node cli.js ingest          # full pipeline for every new chat; resumes after failure
node cli.js status          # progress and spend per chat
node viewer.js              # open http://localhost:4747

Why attention matters

This has been one person's project, tested on one archive. Open-sourcing it properly means taking on the cleanup above, plus support, and that is only worth doing if other people would actually run it. So interest is the deciding signal.
